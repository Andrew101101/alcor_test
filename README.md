# Ручні коригування рядка нарахування

Proof of concept доменної моделі для історії ручних коригувань рядка нарахування (earning line) у payroll-системі.

Фахівець із розрахунку зарплати переглядає рядок, базове значення якого система розраховує автоматично,
і може скоригувати його сумою зі знаком «+» або «−». До кожного коригування обов'язковий коментар.
Усі коригування зберігаються в історії, до якої можна лише дописувати. Після першого ручного коригування
системні перерахунки більше не впливають на рядок.

Модель побудована на **DDD**, **Event Sourcing** і простому розділенні **CQRS**.
Фреймворку, UI та бази даних немає: модель перевіряється тестами PHPUnit.

## Вимоги

- PHP **8.4.1+** (вимога PHPUnit 13) з розширенням `mbstring`
- Composer

## Бізнес-правила і де вони реалізовані

| Правило | Реалізація |
|---------|------------|
| Рядок може отримувати багато коригувань із часом | `EarningLine::addAdjustment()` щоразу записує подію `ManualAdjustmentAdded` |
| Збережене коригування не можна змінити чи видалити | Події та `Adjustment` — `readonly`; `EventStore` має лише `append()` і `load()` |
| Помилку виправляють новим компенсувальним коригуванням | Операцій оновлення чи видалення немає; виправлення — це звичайне коригування |
| Перше ручне коригування заморожує рядок | `EarningLine::isLocked()`; `recalculate()` для замороженого рядка нічого не робить |
| Поточне значення та повна історія доступні будь-коли | Запит `GetEarningLineAudit` повертає модель читання `EarningLineAudit` |
| Коментар до коригування обов'язковий | Value object `Comment` не приймає порожній текст чи текст лише з пробілів |

## Архітектура

```
src/
├── Domain/            бізнес-правила, без залежностей від інших шарів
│   ├── EarningLine.php            агрегат (event sourced)
│   ├── Adjustment.php             одне коригування у стані агрегата
│   ├── Money.php, Comment.php,    value objects
│   │   EarningLineId.php
│   ├── Enums/Currency.php
│   ├── Events/                    SystemValueCalculated, ManualAdjustmentAdded
│   ├── DomainEvent.php            контракт події
│   ├── EventStore.php             контракт сховища (лише дописування)
│   └── Exceptions/                порушення доменних правил
├── Application/       сценарії використання
│   ├── Command/                   команди та їхні обробники (запис)
│   ├── Query/                     запит історії, обробник і DTO (читання)
│   └── Exceptions/                EarningLineNotFound, EarningLineAlreadyExists
└── Infrastructure/
    └── InMemoryEventStore.php     реалізація EventStore для тестів
```

Залежності спрямовані всередину: `Infrastructure` → `Application` → `Domain`.
Домен визначає інтерфейс `EventStore`, а інфраструктура його реалізує.
Обробники отримують інтерфейс через конструктор (dependency injection), тому сховище в пам'яті
можна замінити на базу даних без змін у домені чи шарі застосунку.

### Запис: команди

| Команда | Що відбувається |
|---------|-----------------|
| `CalculateEarningLine` | Створює новий рядок. Якщо потік подій уже існує — `EarningLineAlreadyExists`. |
| `RecalculateEarningLine` | Система отримала нове значення. Ігнорується, якщо рядок заморожений або значення не змінилося. |
| `AddManualAdjustment` | Фахівець додає коригування зі знаком і коментарем. Заморожує рядок. |

Кожен обробник працює за однією схемою і не містить власних бізнес-правил:

```
завантажити події → EarningLine::reconstitute() → викликати метод агрегата → append(releaseEvents())
```

### Event sourcing усередині агрегата

- Методи-команди (`calculate`, `recalculate`, `addAdjustment`) лише перевіряють правила й викликають `recordThat()`.
- Стан змінюється тільки в `apply()`, який виконується і для нових подій, і під час відтворення збережених.
  Тому відтворення завжди дає точно той самий стан.
- `reconstitute()` відтворює події через `apply()` і нічого не записує, тож завантаження рядка не дублює історію.
- `releaseEvents()` віддає нові, ще не збережені події та очищає їх.
- Поточне значення не зберігається, а обчислюється як `системне значення + Σ коригувань`.
  Номери коригувань (#1, #2, …) виводяться з порядку подій.

### Читання: запит

`GetEarningLineAudit` повертає DTO `EarningLineAudit`, а не агрегат, тож код, який лише читає,
не може викликати на ньому команду. DTO містить системне значення, час його останнього розрахунку,
список коригувань (номер, сума, коментар, час), поточне значення та ознаку заморожування.

## Приклад із завдання

Уся таблиця перевіряється двічі: тестом агрегата `tests/Domain/EarningLineTest.php` і наскрізно через команди
тестом `tests/Application/AssignmentScenarioTest.php`. Другий тест перед кожним кроком заново завантажує
рядок зі сховища подій.

| Крок | Дія | Значення після |
|------|-----|----------------|
| 1 | Система розраховує | $1,000.00 |
| 2 | Система перераховує | $1,050.00 |
| 3 | Коригування −$45.55 | $1,004.45 |
| 4 | Система перераховує → ігнорується, подія не зберігається | $1,004.45 |
| 5 | Коригування +$100.10 | $1,104.55 |
| 6 | Коригування −$0.10 | $1,104.45 |
| 7 | Коригування −$0.20 | $1,104.25 |
| 8 | Коригування +$0.20 (компенсує коригування #4 з кроку 7) | $1,104.45 |

У потоці 7 подій: 2 × `SystemValueCalculated` і 5 × `ManualAdjustmentAdded`.

## Припущення

- **Проігнорований перерахунок не залишає сліду.** Якщо аудиторам потрібно бачити такі спроби, легко додати
  подію `SystemRecalculationIgnored`.
- **Перерахунок із тим самим значенням нічого не записує**, щоб не засмічувати історію.
- **Нульове коригування заборонене.** Воно нічого не змінює і лише додало б порожній запис в історію.
- **Коментар обрізається від пробілів і має не більше 500 символів**. Рахуються символи, а не байти.
- **Гроші зберігаються як ціле число центів**, ніколи не float. Рядок має одну валюту. Коригування чи перерахунок
  в іншій валюті відхиляються ще до запису події: некоректну подію з потоку, до якого лише дописують,
  уже неможливо прибрати.
- **Ідентифікатор рядка генерує той, хто викликає** (UUID v4). Команда нічого не повертає, тож id має бути
  відомий заздалегідь.
- **Повторний розрахунок наявного рядка — помилка**, а не неявний перерахунок. Без цієї перевірки другий
  розрахунок дописав би нове системне значення після ручних коригувань і обійшов би заморожування.
- **Час події береться із системного годинника** в конструкторі події. Під час відтворення збережений час
  передається явно, тож історія зберігає початкові позначки часу.

## Спрощення та можливі наступні кроки

- **Модель читання.** Обробник запиту відтворює агрегат замість окремої проєкції. Повна версія CQRS —
  проєктор, що будує історію аудиту безпосередньо з подій.
- **Конкурентний доступ.** `append()` не перевіряє очікувану версію потоку. Дві одночасні зміни одного рядка
  можуть перемішатися; оптимістичне блокування відхилило б другу.
- **Явний зв'язок між коригуваннями.** Компенсувальне коригування зараз посилається на виправлене лише
  в коментарі. Можна додати посилання на номер коригування, яке ми виправляємо.
- **Автор коригування.** Хто вніс коригування, поки що не моделюється.
- **Форматування.** `Money::getFormatted()` розміщено в домені для зручності. Окремий форматер прибрав би
  відображення з моделі.
